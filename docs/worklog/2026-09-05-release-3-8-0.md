# 2026-09-05 — выпуск v3.8.0

Первый выпуск после того, как README догнал код. Тег `v3.7.0` стоял на
коммите, где история выпусков в README обрывалась на v3.3.0; разделы v3.4–v3.7
были дописаны задним числом уже после тега. Поэтому «Не выпущено» на момент
выкатки описывал не всё, что накопилось: тридцать пять коммитов против пяти
пунктов.

## Что попало в раздел дополнительно

Сверка `git log v3.7.0..HEAD` с текстом раздела дала четыре изменения, заметных
человеку, но не описанных:

- `CLAUDE.md` на выбранном языке (был только английский шаблон);
- хуки на Windows теряли доводы команд — команда шла через `cmd.exe`;
- `--force` перезаписывал правленое правило без копии;
- путь не того вида обрывал всю установку, а не один файл.

Остальные коммиты после тега — рефакторинг установщика, тесты и журналы — в
README не выносятся: снаружи их не видно.

## Что проверять первым, если сломается

- **npm показывает прежнюю версию сразу после выкатки** — это не поломка.
  Реестр отвечает «Your package is being processed and may take a few minutes
  to become available», `dist-tags` обновляется с задержкой. Смотреть на строку
  `+ claude-protocol@<версия>` в логе шага «Publish to npm», а не на
  `npm view`.
- **`npm warn publish "bin[claude-protocol]" script name scripts/cli.js was
  invalid and removed`** — тоже не поломка: npm срезает ведущее `./` в пути.
  В опубликованном пакете `bin` на месте, проверяется через
  `npm view claude-protocol@<версия> bin`.
- **Версия в четырёх местах** (`package.json`, `.claude-plugin/plugin.json`,
  два поля в `.claude-plugin/marketplace.json`) — держит тест
  `TestPluginManifests::test_one_version_in_three_places`.

## Что осознанно не тронуто

- Разделы v3.4–v3.7 в обоих README — переписаны не были, хотя часть описанных
  там изменений влилась уже после своего тега. Перекраивать закрытую историю
  выпусков дороже, чем оставить как есть.
- Предупреждение сборки про Node 20 в действиях GitHub — отдельная работа.

## Действия GitHub переведены на Node 24

Сборка выпуска предупреждала, что четыре действия рассчитаны на Node 20 и
запускаются на Node 24 принудительно. Подняты до последних:
`actions/checkout@v7`, `actions/setup-node@v7`, `actions/setup-python@v7`,
`softprops/action-gh-release@v3` — все четыре объявляют `using: node24`.

Два ломающих изменения проверены до правки, а не после:

- **`setup-node` с v5 сам включает кэш npm.** Кэш без файла блокировок ломает
  шаг. Читал `src/main.ts` в теге v7.0.0: автокэш включается только когда в
  `package.json` есть поле `packageManager` со значением `npm`. У нас его нет,
  файл блокировок в репозиторий не входит — не срабатывает. Появится поле —
  надо будет добавить `package-manager-cache: false`, это же советует
  документация действия для публикующих заданий из-за риска отравления кэша.
- **`setup-node` v7 больше не экспортирует пустышку `NODE_AUTH_TOKEN`.** Строка
  `_authToken=${NODE_AUTH_TOKEN}` в `.npmrc` остаётся, но при доверенной
  публикации npm получает короткоживущий токен по OIDC сам. Ровно этот пример
  приведён в документации `setup-node` как рабочий.

Проверено прогоном: временная ветка `ci-check-actions` с копией задания
`test`, запуск 33956246523 — успешно за 16 секунд, ни одного предупреждения об
устаревании и ни одной пометки. Ветка удалена. `action-gh-release` прогоном не
покрыт (он только в задании публикации): у него сверено, что вход
`generate_release_notes` в v3 на месте. Настоящая проверка — следующий выпуск.

## Что проверять первым, если сборка выпуска упадёт

- **`E404 Not Found` на публикации** — доверенный издатель в npm сверяет
  владельца, репозиторий и **имя файла сборки**. `release.yml` переименовывать
  нельзя, не поправив настройку на npmjs.com.
- **`Dependencies lock file is not found`** — значит в `package.json` появилось
  поле `packageManager`, и `setup-node` включил кэш. Лечится
  `package-manager-cache: false`.
